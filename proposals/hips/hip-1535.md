# HIP-1535: CLPR - A Cross Ledger Protocol for Hiero

## Summary

This proposal adds SDK support for **CLPR** ("Clipper"), the Cross Ledger Protocol defined by [HIP-1535](https://github.com/hiero-ledger/hiero-improvement-proposals/blob/4f5da41a527ad6b3a52f5b6d8f39e31565426035/HIP/hip-1535.md). It defines typed HAPI transactions and queries, ownership-proof helpers, response models and compatibility tests.

**Phase 2 scope:** all eight public HAPI transactions, both paid HAPI proof queries (`ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery`), and both mirror node lookups (`MirrorNodeClprChannelQuery` and `MirrorNodeClprConnectorQuery`). The SDK does not wrap `evictPeerEndpoint`; it is an operator safeguard submitted through existing operator tooling. Its functionality code and status value are still mapped, see [RequestType](#requesttype). There is no `redactMessage` RPC. Endpoint sync, node publication/maintenance, endpoint eviction, verifier implementations and application contracts are outside the SDK implementation.

**Final baseline:** consensus node `v0.80.0` from the `release/0.80` branch. Encoding follows the CLPR EAP-0.2 specification. The upstream target for the final security-inclusive tag, final encodings and shared test vectors is November 18, 2026; this is an upstream delivery target, not an SDK release date. Neither `release/0.80` nor a final `v0.80.0` tag existed when this revision was prepared (the latest tag was `v0.80.0-alpha.5`), and the EAP-0.2 specification snapshot is not publicly linkable from this document. Encoding details below that are not in a merged source are marked provisional.

**Interim sources.** Each source is pinned separately; a change to one does not move the others. Re-verify every row against the final baseline before implementation is closed.

## New APIs

New types follow the existing SDK conventions for native-service transactions (e.g. `TopicCreateTransaction`) and queries (e.g. `AccountInfoQuery`).
Fixed-length byte fields are represented as `bytes` per the [API Guidelines](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/guides/api-guideline.md) - SDKs should validate the documented fixed lengths client-side before submission where practical.
Setters/getters are the standard per-field accessors and are omitted below. Transaction and query builders are mutable until frozen/executed; response and value fields are immutable.
None of the eight transaction bodies is present in the pinned `SchedulableTransactionBody`; reject `schedule()` locally for all eight rather than serializing an unsupported scheduled body.

### ClprSignatureScheme

```text
enum ClprSignatureScheme {
    ECDSA_SECP256K1
    ED25519
}
```

**Purpose:** identifies which signing scheme a commit-reveal proof used, so the consensus node knows how to verify the accompanying `publicKey`/`signature` pair.

Key/signature encoding for the commit-reveal proofs below.
`ECDSA_SECP256K1` (default) uses a 64-byte uncompressed public key (`x || y`, no `0x04` prefix) and a 64-byte `r || s` signature.
`ED25519` uses a 32-byte public key and a 64-byte signature.
This is still a wire-level field on every commit-reveal proof, but SDKs should not expose it as an independently settable value, to avoid a caller supplying a scheme/key/signature combination that doesn't actually match - see the `setOwnershipProof` methods on `ClprCompleteChannelTransaction`/`ClprCompleteConnectorTransaction` below, which derive it automatically rather than accepting it as a separate, possibly-inconsistent input.

### ClprRegisterChannelTransaction

**Purpose:** begins establishing a new cross-ledger Channel by staking a claim on a Channel ID without revealing it, so no one else can race to claim the same ID first.

Phase 1 (Commit) of the two-phase channel-establishment scheme. Permissionless - any payer may submit. Duplicate commitments fail with `CLPR_CHANNEL_ALREADY_EXISTS`; a completed commitment remains registered, including after closure.

```text
ClprRegisterChannelTransaction extends Transaction {
    @@nullable ownershipCommitment: bytes

    @@static
    bytes computeOwnershipCommitment(channelId: bytes, publicKey: PublicKey)
}
```

- `ownershipCommitment` - 32-byte `keccak256(channel_id || public_key)`. Reveals neither value, preventing a cross-ledger front-runner from claiming the same Channel ID before the registrant reveals it.
- `computeOwnershipCommitment` - proposed helper accepting a 32-byte Channel ID and an SDK `PublicKey`. Derive the scheme from the key and use the canonical encoding above, including decompression to 64-byte `x || y` for secp256k1. Do not concatenate JS `PublicKey.toBytesRaw()` directly: its secp256k1 output is compressed. Reject unsupported key types and invalid ID lengths locally; do not mutate a transaction.

### ClprCompleteChannelTransaction

**Purpose:** finishes establishing a Channel by revealing the committed identity and activating it, so cross-ledger messaging can begin.

Phase 2 (Reveal). Verifies the commitment preimage and signature, authenticates the peer's configuration via the named verifier contract, and activates the Channel.

```text
ClprCompleteChannelTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable verifierContract: ContractId
    @@nullable configProofBytes: bytes
    @@nullable endpointManifestProofBytes: bytes

    ClprCompleteChannelTransaction setOwnershipProof(privateKey: PrivateKey)
    @@nullable bytes getPublicKey()
    @@nullable bytes getSignature()
    @@nullable ClprSignatureScheme getSignatureScheme()
}
```

- `channelId` - 32 bytes, identical value used in `registerChannel`, identical on both ledgers.
- `setOwnershipProof` - proposed SDK convenience: require `channelId`, `verifierContract`, `configProofBytes` and `endpointManifestProofBytes` first, derive `publicKey` and `signatureScheme` from the key, and sign the 32-byte digest `keccak256("hiero.clpr.complete-channel.v1" || channelId || keccak256(verifierContractProto) || keccak256(configProofBytes) || keccak256(endpointManifestProofBytes))`. This digest is **provisional**: it follows open [#28017](https://github.com/hiero-ledger/hiero-consensus-node/pull/28017) at 807100e2, while merged `main` still verifies a signature over `keccak256(channelId)` only. Replace it with the final EAP-0.2 encoding when the final baseline is published, and keep the encoding in one place per SDK so that change does not touch the public API. The domain string is UTF-8 without a terminator; `verifierContractProto` is the protobuf serialization of the `ContractID` exactly as it is set in the transaction body, so the SDK must hash the same bytes it serializes. With the current JS/Java/Go `PrivateKey.sign()` APIs, pass the unhashed preimage for ECDSA because that API already applies keccak256; pass the digest for Ed25519 because that API signs its input bytes directly. A raw-digest ECDSA primitive instead receives the digest. Do not hash twice or apply a message prefix. Use the same public-key encoding as the commitment; do not retain the private key.
- Proof getters are nullable and return the stored wire values, including after `Transaction.fromBytes()`, without requiring a private key. A missing or invalidated proof returns null; when present, derive the scheme from the helper or decode it from the wire, including the protobuf ECDSA default. Changing any of the four bound fields clears all three proof values. Freezing/executing without a complete proof fails locally; an unchanged decoded proof may be re-serialized without rebuilding it. There are no independent setters for these proof fields.
- `verifierContract` - the `ContractId` of a supported built-in verifier (currently system addresses `0x16e` through `0x171`) or a deployed verifier contract; immutable for the Channel's lifetime.
- `configProofBytes` - opaque proof passed to the verifier's `verifyConfig` to authenticate the peer's `ClprLedgerConfiguration` (which carries the peer's initial trust anchor).
- `endpointManifestProofBytes` - opaque proof attesting the peer's initial `ClprEndpointManifest`. An empty endpoint list is valid, but this does not imply empty proof bytes are valid: the Hiero TSS verifier rejects them. Other verifier families may support a synthesized bring-up manifest. Callers must supply the proof encoding accepted by the selected verifier.

### ClprCloseChannelTransaction

**Purpose:** shuts down a Channel (or cleans up an abandoned registration) so it stops accepting new outbound messages.

Requires the network's **Treasury or System Admin account** - the same superuser privilege that gates freeze, software-update, and fee-schedule transactions (`PrivilegesVerifier.checkClprAdmin` simply calls the existing `isSuperUser` check).
There is no separate, delegatable CLPR-specific admin key or role, despite the "CLPR Service Admin" terminology used elsewhere.
This same authorization gates `ClprUpdateLedgerConfigurationTransaction` below. Registration/completion and the pinned bundle handler are permissionless; Connector deregistration has its own required signatures.
Closing an `ACTIVE` or `PAUSED` Channel enters `CLOSING`, or `DRAINED` if its queue is already acknowledged. Closing a `DRAINED` Channel transitions it to `CLOSED`. It can also delete an abandoned `PENDING` commitment that was never completed.

```text
ClprCloseChannelTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable ownershipCommitment: bytes
}
```

- `ownershipCommitment` - only required/used when no Channel exists yet for `channelId` (sweeping an abandoned `registerChannel` commitment); ignored when an active Channel record is found.

### ClprSubmitBundleTransaction

**Purpose:** delivers a batch of cross-ledger messages, plus the state proof authenticating them, from a peer ledger's endpoint into this ledger's CLPR Service.

Submits a bundle of messages synced from a peer ledger's endpoint. The pinned implementation permits any payer under its default API permissions: ingest checks CLPR enablement and `preHandle` adds no endpoint-identity requirement. In the selected fee branch, a rejected bundle, including one rejected with `CLPR_NO_PROGRESS`, costs the payer only its transaction fee; there is no separate endpoint penalty. Merged `main` still charges an endpoint misbehavior penalty on the no-progress path, so do not promise penalty-free rejection until the final baseline confirms it. In the fee branch, bundles are exempt from the node and network fee components, and the service fee covers the bundle bytes and the verifier's measured gas (see [Fees](#fees)).

```text
ClprSubmitBundleTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable bundlePayload: bytes
}
```

- `bundlePayload` - opaque to the SDK and to the protocol; interpreted only by the Channel's verifier contract. Preserve empty bytes and do not impose a non-empty constraint: CN [pure checks accept an empty payload as an acknowledgement-only bundle](https://github.com/hiero-ledger/hiero-consensus-node/blob/77c8361520e595c25d2d943f89a57b32cb21d22c/hedera-node/hedera-clpr-service-impl/src/main/java/com/hedera/node/app/service/clpr/impl/handlers/ClprSubmitBundleHandler.java#L122-L127). Empty bytes must still satisfy the selected verifier and the later handler checks; the SDK does not promise that an empty bundle is accepted.

The wire format also carries deprecated `endpointNodeId`/`endpointSignature` fields that the pinned handler ignores; do not expose them as SDK setters or imply they authenticate the caller. The proto describes address-book endpoint authority, but the handler does not enforce it. CN must confirm the intended authority contract; endpoint-only submission remains an open requirement, not current enforced behavior. The SDK wrapper adds no relay/discovery behavior.

### ClprRegisterConnectorTransaction

**Purpose:** begins registering a Connector - the economic actor that will authorize and pay for cross-ledger message execution - by staking a claim on its identity without revealing it.

Phase 1 (Commit) for Connector registration. Permissionless. The referenced Channel must already exist, or the transaction fails with `CLPR_CHANNEL_NOT_FOUND`. Duplicate commitments fail with `CLPR_CONNECTOR_ALREADY_EXISTS`; commitments remain registered after completion and deregistration, so reuse is rejected.

```text
ClprRegisterConnectorTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable commitment: bytes

    @@static
    bytes computeConnectorId(channelId: bytes, publicKey: PublicKey, salt: bytes)
    @@static
    bytes computeOwnershipCommitment(connectorId: bytes, publicKey: PublicKey)
}
```

- `channelId` - required, exactly 32 bytes; the existing Channel the Connector is intended for. Use the same value when computing the Connector ID and when completing the Connector.
- `commitment` - 32-byte `keccak256(connectorId || publicKey)`, where `connectorId = keccak256(channelId || publicKey || salt)`.
- `computeConnectorId` and `computeOwnershipCommitment` - proposed helpers applying those formulas with the same canonical `PublicKey` encoding as the Channel helper. Require 32-byte IDs and salt and reject unsupported keys locally. Call the ID helper first, then the commitment helper; neither signs, retains a private key or mutates a transaction.

### ClprCompleteConnectorTransaction

**Purpose:** finishes registering a Connector by revealing its identity, posting its slashable stake, and activating it to authorize and pay for messages.

Phase 2 (Reveal). Requires an existing Channel. Creates the Connector, keyed by `(channelId, connectorId)`, once the derived ID, commitment preimage and signature are verified; the payer funds the locked stake. **Provisional:** under open [#28013](https://github.com/hiero-ledger/hiero-consensus-node/pull/28013) at 583784f7, the key of `connectorContract` must also sign the transaction, because message delivery debits that contract's balance. A missing, deleted or non-contract account, or a contract without a usable key, is rejected with `CLPR_INVALID_CONNECTOR_CONTRACT`. Merged `main` does not require this signature. The SDK adds no new API for it: callers sign with the contract's key through the existing transaction-signing APIs.

```text
ClprCompleteConnectorTransaction extends Transaction {
    @@nullable connectorId: bytes
    @@nullable salt: bytes
    @@nullable channelId: bytes
    @@nullable connectorContract: ContractId
    @@nullable adminKey: Key
    lockedStake: Hbar

    ClprCompleteConnectorTransaction setOwnershipProof(privateKey: PrivateKey)
    @@nullable bytes getPublicKey()
    @@nullable bytes getSignature()
    @@nullable ClprSignatureScheme getSignatureScheme()
}
```

- `connectorId` - exactly 32 bytes, re-derived by the handler as `keccak256(channelId || publicKey || salt)`.
- `salt` - exactly 32 bytes; all-zero is valid for a single Connector.
- `setOwnershipProof` - proposed SDK convenience with the same key/signature encoding as Channel completion. Require `channelId`, `connectorId`, `salt`, `connectorContract` and `adminKey` first; validate the derived Connector ID, then sign the digest `keccak256("hiero.clpr.complete-connector.v1" || channelId || connectorId || clprServiceAddress || keccak256(connectorContractProto) || keccak256(adminKeyProto))`. This digest is **provisional**: it follows open [#28019](https://github.com/hiero-ledger/hiero-consensus-node/pull/28019) at 453306c6, while merged `main` still verifies a signature over `keccak256(connectorId || clprServiceAddress)`. Replace it with the final EAP-0.2 encoding as for Channel completion. The service address is the 20 bytes `0x000000000000000000000000000000000000016e`; `connectorContractProto` and `adminKeyProto` are the protobuf serializations of the `ContractID` and `Key` exactly as they are set in the transaction body. For the current SDK `PrivateKey.sign()` APIs, pass the unhashed preimage to ECDSA and its keccak256 digest to Ed25519. Changing any of the five bound fields clears the proof. The nullable getters and `Transaction.fromBytes()` behavior match Channel completion; freezing/executing requires a complete proof. Do not retain the private key or expose independent setters for its three proof fields.
- `connectorContract` - the local authorization contract governing message dispatch for this Connector; must refer to an already-deployed contract with a key, and that key must sign.
- `adminKey` - required; authorizes future `deregisterConnector`. Uses the SDK's existing `Key` abstraction (any key type/threshold key supported elsewhere).
- `lockedStake` - slashable `Hbar` bond, encoded as unsigned tinybars on the wire. Use the portable `Hbar` range of 0 through 2^63-1 tinybars and reject negative values, fractions of a tinybar or unrepresentable amounts before serialization. In the selected fee branch, the network minimum is set in USD (`clpr.minLockedStakeTinycents`, temporary default $3,000) and converted to tinybars at the active exchange rate at consensus time, so the SDK cannot check it locally; a stake below it fails with `CLPR_INSUFFICIENT_STAKE`. Locked stake is not revalued when the exchange rate changes.

### ClprDeregisterConnectorTransaction

**Purpose:** retires a Connector that's no longer needed and returns its locked stake to a designated recipient.

Requires the Connector's `adminKey` to sign. Removes the Connector and returns its locked stake.

```text
ClprDeregisterConnectorTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable connectorId: bytes
    @@nullable stakeRecipient: AccountId
}
```

- `stakeRecipient` - must be explicitly specified and must itself sign the transaction (in addition to the Connector's `adminKey`).

### ClprUpdateLedgerConfigurationTransaction

**Purpose:** lets the network admin adjust this ledger's CLPR capacity limits (`ClprThrottles`) after genesis.

Requires the network's Treasury or System Admin account (see `ClprCloseChannelTransaction` above).
Updates the local ledger's throttle configuration by replacing the entire throttles object, not patching individual fields. Read the current values with `ClprGetLedgerConfigurationQuery`, construct a new `ClprThrottles` with the desired changes and all seven values, then submit it. The SDK serializes only `configuration.throttles`; it does not expose setters for genesis/server-owned fields.
`chainId`, `protocolVersion`, and `timestamp` on the supplied configuration are ignored by the handler - the first two are immutable (set at genesis), and the timestamp is stamped automatically.

`ClprThrottles` fields are validated before acceptance.
`maxMessagesPerBundle`, `maxMessagePayloadBytes`, `maxQueueDepth`, `maxGasPerMessage`, and `maxSyncBytes` must all be strictly positive (`0` fails with `INVALID_CLPR_CONFIGURATION`); `maxLocalEndpoints`/`maxPeerEndpoints` are the exception, where `0` means "no limit."
The handler also enforces a deadlock guard: `maxSyncBytes` must be at least `maxMessagePayloadBytes + 65,536` bytes, so a bundle carrying one max-sized message always has room for its proof/envelope overhead.
Without this floor a Channel could be configured into a permanent stall, since the sender could never assemble a bundle that fits, the peer would never acknowledge, and the queue would never drain.

```text
ClprUpdateLedgerConfigurationTransaction extends Transaction {
    @@nullable throttles: ClprThrottles
}
```

### ClprThrottles

**Purpose:** the set of capacity limits a ledger enforces on its CLPR Service - message size, bundle size, queue depth, and endpoint counts.

```text
ClprThrottles {
    @@immutable maxMessagesPerBundle: uint32
    @@immutable maxMessagePayloadBytes: uint32
    @@immutable maxGasPerMessage: uint64
    @@immutable maxQueueDepth: uint32
    @@immutable maxSyncBytes: uint64
    @@immutable maxLocalEndpoints: uint32
    @@immutable maxPeerEndpoints: uint32

    @@static
    ClprThrottles of(
        maxMessagesPerBundle: uint32,
        maxMessagePayloadBytes: uint32,
        maxGasPerMessage: uint64,
        maxQueueDepth: uint32,
        maxSyncBytes: uint64,
        maxLocalEndpoints: uint32,
        maxPeerEndpoints: uint32
    )
}
```

Capacity limits advertised by a ledger's CLPR Service. The proposed factory requires every field and validates the positive-value and `maxSyncBytes` floor rules above; zero endpoint limits remain valid. Language-specific constructors may provide the equivalent operation. Immutable fields do not imply an output-only type.

### ClprGetLedgerConfigurationQuery

**Purpose:** reads a ledger's current CLPR configuration, typically to obtain the state proof material needed to establish a Channel with it.

```text
ClprGetLedgerConfigurationQuery extends Query<ClprLedgerConfigurationInfo> {
}
```

Paid public read when CLPR is enabled; no admin authorization is required. It uses the standard paid-query flow (cost query, then a query payment), because building and verifying the state proof costs real work (see [Fees](#fees)). This is the selected fee-branch behavior; merged `main` still serves the query free. Use the standard query-cost and payment mechanisms rather than a CLPR-specific price. Takes no CLPR-specific parameters beyond the standard query header.

### ClprLedgerConfigurationInfo

**Purpose:** the response payload for `ClprGetLedgerConfigurationQuery`.

```text
ClprLedgerConfigurationInfo {
    @@immutable protocolVersion: uint32
    @@immutable chainId: string
    @@immutable serviceAddress: bytes
    @@immutable timestamp: dateTime
    @@immutable throttles: ClprThrottles
    @@immutable initialTrustAnchor: bytes
    @@immutable initialTrustAnchorId: bytes
    @@immutable configurationStateProof: bytes
}
```

- `chainId` - CAIP-2 identifier. A Hiero ledger derives it at genesis from its EVM chain ID as `eip155:<contracts.chainId>`, e.g. `eip155:295` for mainnet and `eip155:296` for testnet; an Ethereum peer reports e.g. `eip155:1`.
- `configurationStateProof` - opaque serialized state proof from a signed snapshot; pass it unchanged as `configProofBytes` only when the peer verifier accepts that encoding. The pinned handler returns live configuration fields alongside a snapshot proof, so the SDK must not claim the proof authenticates those exact live values. It may be empty when no usable snapshot exists or configured sender-side proof validation fails. Preserve an empty proof as a successful read with unavailable proof material; applications needing proof should re-query with bounded retry.

### ClprGetEndpointManifestQuery

**Purpose:** reads a ledger's current set of CLPR relay endpoints, used to seed or recover a Channel's peer endpoint cache.

```text
ClprGetEndpointManifestQuery extends Query<ClprEndpointManifestInfo> {
}
```

Paid public read when CLPR is enabled - no admin authorization required; priced like `ClprGetLedgerConfigurationQuery`.
With a usable signed snapshot, returns its endpoint manifest and matching proof, used both to seed a new Channel's peer manifest and to construct manifest-recovery bundles; do not assume this is the newest live manifest.

### ClprEndpointManifestInfo

**Purpose:** the response payload for `ClprGetEndpointManifestQuery`.

```text
ClprEndpointManifestInfo {
    @@immutable version: uint64
    @@immutable serviceAddress: bytes
    @@immutable endpoints: list<ClprEndpoint>
    @@immutable manifestStateProof: bytes
}
```

- `manifestStateProof` - opaque bytes to preserve unchanged. As with `configurationStateProof`, it may be empty before a usable signed snapshot or after configured sender-side validation rejects a proof. An empty proof does not mean the endpoint list is empty and must not be submitted to a verifier that requires proof.

### ClprEndpoint

**Purpose:** describes one CLPR relay endpoint - its network address, TLS identity, and owning account - as it appears in an endpoint manifest.

```text
ClprEndpoint {
    @@immutable serviceEndpoint: ClprServiceEndpoint
    @@immutable tlsCertificate: bytes
    @@immutable accountId: bytes
}
```

- `tlsCertificate` - informational only. Endpoints use ordinary TLS for confidentiality, peers do not validate this certificate, and the consensus node marks the field as slated for deprecation. Do not use it to authenticate an endpoint.
- `accountId` - informational only; the consensus node documents it as not used by the network.

### ClprServiceEndpoint

**Purpose:** the network address (IP and port) of a single CLPR endpoint.

```text
ClprServiceEndpoint {
    @@immutable ipAddress: string
    @@immutable port: uint32
}
```

Numeric IPv4/IPv6 address only - no DNS hostnames, consistent with the SDK's existing `Endpoint`/node-address-book representations elsewhere.

### Contract calls through existing SDK APIs

The SDK adds no dedicated `sendMessage` or queue-state classes. Applications use the existing contract execution and contract call query APIs with the ABIs below. The CLPR system contract is at [address `0x16e` (entity number 366)](https://github.com/hiero-ledger/hiero-consensus-node/blob/77c8361520e595c25d2d943f89a57b32cb21d22c/hedera-node/hedera-clpr-service/src/main/java/com/hedera/node/app/service/clpr/ClprServiceConstants.java#L12-L14); build its `ContractId` with the network's shard and realm.

```text
sendMessage(bytes32 channelId, bytes32 connectorId, bytes targetApplication, bytes messageData) payable returns (uint64 messageId)
getChannelQueueState(bytes32 channelId) payable returns (uint64 receivedMessageId, uint64 ackedMessageId)
```

The [send translator](https://github.com/hiero-ledger/hiero-consensus-node/blob/77c8361520e595c25d2d943f89a57b32cb21d22c/hedera-node/hedera-smart-contract-service-impl/src/main/java/com/hedera/node/app/service/contract/impl/exec/systemcontracts/clpr/sendmessage/SendMessageTranslator.java#L20-L43) and [queue-state translator](https://github.com/hiero-ledger/hiero-consensus-node/blob/77c8361520e595c25d2d943f89a57b32cb21d22c/hedera-node/hedera-smart-contract-service-impl/src/main/java/com/hedera/node/app/service/contract/impl/exec/systemcontracts/clpr/getchannel/GetChannelTranslator.java#L17-L26) define the selectors; the fee branch does not change them. The `getChannel` name used in earlier revisions is obsolete. The queue-state call returns only two counters, not the full Channel model; preserve both as unsigned 64-bit values.

**Funding.** `payable` comes from the selected fee branch's [interface](https://github.com/hiero-ledger/hiero-consensus-node/blob/08036e992bd5db2feba155c11f7676778b861775/hedera-node/test-clients/src/main/resources/contract/contracts/SourceApplication/IClprSystemContract.sol#L12-L26). Each method has a target price. The call pays part of it as gas and must attach the remainder as value; for `sendMessage`, only a successful send is charged that remainder ([pricing](https://github.com/hiero-ledger/hiero-consensus-node/blob/08036e992bd5db2feba155c11f7676778b861775/hedera-node/hedera-smart-contract-service-impl/src/main/java/com/hedera/node/app/service/contract/impl/exec/systemcontracts/clpr/ClprCallPricing.java#L28-L62)). Off-chain contract call queries use the ordinary query payment. Merged `main` declares neither method payable, so examples and ABI fixtures must name the source revision they target. Amounts are in [Fees](#fees).

**Authorization flow.** For application-originated messages, the SDK calls the application contract, the application calls CLPR `sendMessage`, and CLPR then calls the registered Connector contract's `authorizeOutboundMessage` hook, with the CLPR system contract as `msg.sender`, before enqueueing. [SourceApplication](https://github.com/hiero-ledger/hiero-consensus-node/blob/08036e992bd5db2feba155c11f7676778b861775/hedera-node/test-clients/src/main/resources/contract/contracts/SourceApplication/SourceApplication.sol#L39-L46) demonstrates the funded flow. CLPR records the immediate caller as the message sender, so calling `sendMessage` directly from an account, or through a different contract, changes the sender identity the peer application sees. The Connector is an authorization hook, not an SDK-facing forwarding entry point. A rejecting hook fails the send with `CLPR_AUTHORIZATION_FAILED`.

### Mirror node queries

Channel and Connector state is read from the mirror node rather than the consensus node, since the mirror node is what indexes this state. The `getChannelQueueState` contract call exposes only the two queue counters; see [Contract calls through existing SDK APIs](#contract-calls-through-existing-sdk-apis).
This proposal adds only the two reads SDK users need: a Channel's current state and a Connector's current state, each looked up by ID.
Both follow the established mirror node query pattern (`MirrorNodeAccountBalanceQuery`) and the [HTTP Transport Layer](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/proposals/http-transport-layer.md) proposal:

- Each is a standalone class; neither extends `Query`.
- They are free, and eventually consistent: allow for mirror node ingestion lag; no latency bound is established here.

Ledger configuration and the endpoint manifest stay on `ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery` above, because only the consensus node can produce the state proofs they return.

| Question                                                                                                 | Query                                                                 |
|------------------------------------------------------------------------------------------------------- |------------------------------------------------------------------------|
| Is my Channel still `ACTIVE`, or has it moved to `PAUSED`, `CLOSING` or `CLOSED`?                        | `MirrorNodeClprChannelQuery`                                          |
| Is my Channel still configured the way I vetted it: same verifier, verifier fingerprint and peer chain?  | `MirrorNodeClprChannelQuery`                                          |
| Is the Channel's outbound queue draining?                                                                | `MirrorNodeClprChannelQuery`                                          |
| How much stake does my Connector have locked, and has it been slashed?                                   | `MirrorNodeClprConnectorQuery`                                        |
| How many of my Connector's messages are still in flight? Deregistration is blocked until none are.       | `MirrorNodeClprConnectorQuery`                                        |
| What can my Connector still spend on execution?                                                          | Existing `MirrorNodeAccountBalanceQuery` on its `connectorContractId` |

These are what the [CLPR spec](https://github.com/LFDT-CLPR/clpr-spec/blob/945082d69e65dd0fd9e9bdf8d59cb8121579f6fd/clpr-service.md) (§4.2) asks application developers to monitor: "Connector health (balance declining, slashing events)" and "Channel status changes (PAUSED, CLOSING, CLOSED)".

Deliberately not included:

- **Chain or Channel discovery.** The spec tells applications to treat `channel_id` and `connector_id` as configured values, and anyone can claim any chain ID. The SDK therefore offers no "find Channels for a chain" query.
- **Pending registrations.** The `ClprRegisterChannelTransaction` receipt confirms a registration.
- **Message history.** Applications learn each message's outcome on-chain, through their `onClprResponse` callback. Message history is an auditing feature, served by the mirror node REST API and the explorer.

### MirrorNodeClprChannelQuery

**Purpose:** reads one Channel's current state, so an application can confirm the Channel is healthy and still configured the way it was vetted.

```text
MirrorNodeClprChannelQuery {
    @@nullable channelId: bytes

    @@async
    MirrorNodeClprChannel execute(client: Client)
}
```

**Route (mirror node design, [Channels API](https://github.com/hiero-ledger/hiero-mirror-node/blob/0c0a831342b134f05ce81d058e16ebf6bfaa73fb/docs/design/clpr.md#1-channels-api)):** `GET /api/v1/clpr/channels?channel.id=eq:{channelId}`. `channel.id` is the table's primary key, so this is a direct lookup returning at most one row, and the query does not follow `links.next`. A `channel.id` filter matches completed Channels only, never pending commitments. `channelId` is required and must be 32 bytes; `execute` fails before any network call otherwise. Do not send `timestamp`: with `channel.id` it switches the route to an as-of reconstruction, which is outside this query's scope.

### MirrorNodeClprChannel

**Purpose:** a Channel's current state as recorded by the mirror node.

```text
@@finalType
MirrorNodeClprChannel {
    @@immutable channelId: bytes
    @@immutable chainId: string
    @@immutable status: ClprChannelStatus
    @@immutable verifierContractId: ContractId
    @@immutable verifierFingerprint: bytes
    @@immutable trustAnchorId: bytes
    @@immutable nextMessageId: uint64
    @@immutable ackedMessageId: uint64
    @@immutable receivedMessageId: uint64
    @@immutable createdTimestamp: dateTime
    @@immutable modifiedTimestamp: dateTime
}
```

- `chainId` - the peer chain the Channel claims to reach. Anyone can claim any chain ID, so treat it as a check against the application's own configuration, not as proof of the peer's identity.
- `verifierFingerprint` - a fixed identity hash for a built-in verifier, or the keccak256 hash of a deployed verifier's bytecode, for comparison with the value the application vetted. A proxy's bytecode doesn't change when its logic is upgraded, so the fingerprint alone won't reveal an upgrade behind a proxy.
- `nextMessageId`, `ackedMessageId`, `receivedMessageId` - queue positions, returned as JSON numbers; parse them as unsigned 64-bit values without floating-point conversion. The outbound backlog is `nextMessageId - 1 - ackedMessageId`. A backlog that keeps growing while the Channel is `ACTIVE` suggests the peer has stopped acknowledging. Queue counters show acknowledgement, not that an application callback ran.
- `modifiedTimestamp` - mapped from the REST response's `timestamp.from`, when the current state took effect.

### ClprChannelStatus

**Purpose:** a Channel's lifecycle state.

```text
enum ClprChannelStatus {
    ACTIVE
    PAUSED
    CLOSING
    DRAINED
    CLOSED
}
```

The proto also defines `PENDING`, but `MirrorNodeClprChannelQuery` never returns it: the mirror node lists pending commitments under `status=eq:PENDING` without a `channel_id`, and rejects combining that filter with `channel.id`.

### MirrorNodeClprConnectorQuery

**Purpose:** reads one Connector's current state, so its operator, or an application relying on it, can monitor stake, slashing and in-flight messages.

```text
MirrorNodeClprConnectorQuery {
    @@nullable channelId: bytes
    @@nullable connectorId: bytes

    @@async
    MirrorNodeClprConnector execute(client: Client)
}
```

**Route (mirror node design, [Connectors API](https://github.com/hiero-ledger/hiero-mirror-node/blob/0c0a831342b134f05ce81d058e16ebf6bfaa73fb/docs/design/clpr.md#3-connectors-api)):** `GET /api/v1/clpr/channels/{channelId}/connectors?connector.id=eq:{connectorId}&status=eq:ACTIVE`. The Channel ID is a path segment; together with `connector.id` it identifies at most one row, so the query does not follow `links.next`. Filtering on `status=eq:ACTIVE` excludes deregistered and banned Connectors, which the mirror node retains with status `DELETED`. Both IDs are required and must be 32 bytes; `execute` fails before any network call otherwise.

### MirrorNodeClprConnector

**Purpose:** a Connector's current state as recorded by the mirror node.

```text
@@finalType
MirrorNodeClprConnector {
    @@immutable connectorId: bytes
    @@immutable channelId: bytes
    @@immutable connectorContractId: ContractId
    @@immutable adminKey: Key
    @@immutable lockedStake: Hbar
    @@immutable inFlightMessageCount: uint64
    @@immutable slashCount: uint64
    @@immutable createdTimestamp: dateTime
}
```

- `lockedStake` - the remaining slashable `Hbar` stake, decoded losslessly from the REST `locked_stake` tinybar string; reject values outside the portable `Hbar` range rather than wrapping or truncating them. Each slash reduces it.
- `slashCount` - reaching the configured `slashBanThreshold` bans/removes the Connector; the CN default at the source baseline is five, not a fixed protocol constant.
- `inFlightMessageCount` - `ClprDeregisterConnectorTransaction` fails with `CLPR_CONNECTOR_HAS_IN_FLIGHT_MESSAGES` until this reaches zero.
- The Connector's spendable balance is the HBAR balance of `connectorContractId`, which the existing `MirrorNodeAccountBalanceQuery` already returns.

### Mirror node dependencies

The [merged mirror node design](https://github.com/hiero-ledger/hiero-mirror-node/blob/0c0a831342b134f05ce81d058e16ebf6bfaa73fb/docs/design/clpr.md#rest-api-implementation) defines five REST APIs: Channels, messages per Channel, Connectors (nested under a Channel), ledger configuration and endpoint manifest. Pending Channel and Connector registrations are listed with `status=eq:PENDING` rather than separate routes; the November 11 design update also includes pending commitments in an unfiltered Channel list, which does not affect the known-ID lookups above. The design settles the response contract the SDK queries need: the known-ID filters, the verifier fingerprint, trust-anchor ID and all three queue counters on Channels, `timestamp: {from, to}` state ranges, `DELETED` status for retained Connector rows, `locked_stake` as a string and `admin_key` as `{_type, key}`.

Remaining dependencies:

1. **Availability:** the importer and REST implementation is in progress ([#14594](https://github.com/hiero-ledger/hiero-mirror-node/pull/14594), [#14626](https://github.com/hiero-ledger/hiero-mirror-node/pull/14626), [#14636](https://github.com/hiero-ledger/hiero-mirror-node/pull/14636), [#14609](https://github.com/hiero-ledger/hiero-mirror-node/pull/14609)). The design ships mirror node support in lockstep with the consensus node release that enables CLPR. Live acceptance targets mirror node `v0.168`; the latest mirror node release at this revision was `v0.166.2`. Offline request/response mapping can be completed and tested against mocked responses before then.
2. **Ingestion coverage:** integration tests must cover outbound `sendMessage` ingestion, Connector changes during bundle processing (including slashes and bans), and contract-ID resolution. Allow for ingestion lag; a not-found result shortly after a transaction may be transient.
3. **Bundle authority:** current CN handling permits ordinary payers to submit bundles, while HAPI prose describes endpoint authority. Obtain CN confirmation of the intended contract and track any future enforcement change; do not describe the prose restriction as already implemented.

The mirror node monitor's typed-transaction tests depend on Java SDK CLPR support (or a raw-protobuf workaround). That is a monitor-test dependency, not a prerequisite for every importer/REST implementation task.

## Internal Changes

### Response Codes

Import all **34** CLPR-related values in the pinned [HAPI response enum](https://github.com/hiero-ledger/hiero-consensus-node/blob/77c8361520e595c25d2d943f89a57b32cb21d22c/hapi/hedera-protobuf-java-api/src/main/proto/services/response_code.proto), including retained/deprecated values, into SDK status enums and wire conversions. Grouping below describes current handler behavior separately from inactive wire definitions. `CLPR_MESSAGE_NOT_FOUND` remains defined even though the redaction RPC is absent; the other former redaction statuses are absent from this baseline.

A privileged-authority failure (e.g. a non-admin account submitting `ClprCloseChannelTransaction`) surfaces as the standard, pre-existing `AUTHORIZATION_FAILED` code, not a new CLPR-specific code, since CLPR admin checks route through the same `PrivilegesVerifier` path as other privileged transactions (e.g. system-file updates). Don't confuse this with `CLPR_AUTHORIZATION_FAILED` (562) below, a distinct, CLPR-specific code for an unrelated failure - the similar names are a real risk for mix-ups in error-handling code.

#### Ledger configuration (`ClprUpdateLedgerConfigurationTransaction`)

- `CLPR_NOT_ENABLED` (537) - the CLPR service is not enabled on this ledger (`clpr.enabled=false`); returned by every CLPR transaction and query, not just this one.
- `INVALID_CLPR_CONFIGURATION` (538) - a supplied throttle value is invalid, e.g. `maxMessagesPerBundle`, `maxMessagePayloadBytes`, or `maxQueueDepth` is not strictly positive, or the `maxSyncBytes` deadlock-guard floor (`maxMessagePayloadBytes + 65,536`) isn't met.
- `CLPR_CHAIN_ID_IMMUTABLE` (539) - defined for an attempt to change `chainId`, but **not currently reachable**: the handler doesn't throw it at all. It silently keeps the existing `chainId` and discards whatever value was submitted (see Test Plan #17). Confirm with the working group whether active rejection is actually intended, since the wire-level code exists but isn't wired up.
- `CLPR_TOO_MANY_SEED_ENDPOINTS` (540) - retained wire definition; no active throw path in the pinned update handler, which no longer updates the deprecated seed-endpoint list.
- `CLPR_INVALID_SEED_ENDPOINT` (541) - retained wire definition; no active throw path in the pinned update handler.

#### Channel lifecycle (`ClprRegisterChannelTransaction` / `ClprCompleteChannelTransaction` / `ClprCloseChannelTransaction`)

- `CLPR_CHANNEL_ALREADY_EXISTS` (542) - the commitment was already registered, or completion conflicts with a Channel that cannot be completed in its current state.
- `CLPR_INVALID_SIGNATURE` (543) - the reveal-phase signature doesn't verify against the supplied public key. Also returned by `ClprCompleteConnectorTransaction` for the same reason.
- `CLPR_INVALID_VERIFIER_CONTRACT` (544) - the supplied verifier is neither a supported built-in nor a valid deployed smart contract.
- `CLPR_VERIFIER_CONFIG_FAILED` (545) - the verifier contract's `verifyConfig` call failed or returned invalid data.
- `CLPR_COMMITMENT_MISMATCH` (546) - `keccak256(channelId || publicKey)` doesn't match any stored commitment. Also returned by `ClprCompleteConnectorTransaction` for the equivalent connector-commitment check.
- `CLPR_CHANNEL_NOT_FOUND` (547) - the specified `channelId` doesn't correspond to any known Channel.
- `CLPR_INVALID_CHANNEL_STATUS` (548) - the Channel's current status doesn't allow the requested transition (e.g. closing an already-`CLOSING`/`CLOSED` Channel).

#### Retained message status

- `CLPR_MESSAGE_NOT_FOUND` (549) - retained in the wire enum; no active throw path in the pinned handlers. Map it without requiring a redaction API or a live negative test.

#### Bundle submission and message dispatch (`ClprSubmitBundleTransaction`)

- `CLPR_INVALID_ENDPOINT_SIGNATURE` (551) - retained wire definition; no active throw path in the pinned bundle handler. The deprecated signature field is ignored, so do not document an active signature-validation check.
- `CLPR_BUNDLE_VERIFICATION_FAILED` (552) - the Channel's verifier contract rejected the bundle's state proof.
- `CLPR_RUNNING_HASH_MISMATCH` (553) - the bundle's running hash doesn't match the Channel's expected value.
- `CLPR_PAYLOAD_TOO_LARGE` (561) - the raw bundle exceeds local `maxSyncBytes`, or an inbound message exceeds local `maxMessagePayloadBytes`. Also returned outbound from `sendMessage` against the peer's advertised payload limit.
- `CLPR_BUNDLE_DECODE_FAILED` (568) - a per-message protobuf decode failed *inside a verifier-accepted bundle*. Since the verifier already attested to the bundle's contents, this specifically means the verifier signed off on malformed data - a stronger signal than an ordinary input-validation failure, since it implies a bug or compromise in the Channel's verifier rather than just a bad caller input. Processing stops. The handler writes `PAUSED` before throwing, but the transaction dispatcher rolls back on that exception without a replay callback. Persisted pause is therefore an unresolved CN behavior, not an SDK guarantee; obtain CN confirmation and integration evidence before asserting it.
- `CLPR_EMPTY_BUNDLE` (569) - **deprecated**, superseded by `CLPR_NO_PROGRESS` below. SDKs should recognize both for wire compatibility with older/newer nodes but should not document this one as the primary code.
- `CLPR_RATE_LIMITED` (570) - defined for an endpoint that exceeds its fair share of the ledger's bundle-submission throttle (`max_bundles_per_sec / num_registered_endpoints`), per its protobuf doc comment, but **not currently reachable**: no per-endpoint throttle-sharing check exists anywhere in `ClprSubmitBundleHandler` today. Treat the formula as the documented intent, not current behavior, until that check is implemented. See the Transaction Retry note below for the implication once it is.
- `CLPR_NO_PROGRESS` (571) - the bundle satisfies none of the **five** Bundle Progress Criteria the handler actually checks: new messages, trust-anchor advancement, ack progress, a Channel status transition (e.g. `CLOSING` -> `DRAINED`), or endpoint-manifest advancement. In the selected fee branch the payer pays only the transaction fee, with no additional endpoint penalty; merged `main` still applies the penalty (see [ClprSubmitBundleTransaction](#clprsubmitbundletransaction)).

#### Connector lifecycle (`ClprRegisterConnectorTransaction` / `ClprCompleteConnectorTransaction` / `ClprDeregisterConnectorTransaction`)

- `CLPR_CONNECTOR_NOT_FOUND` (555) - the specified Connector doesn't exist.
- `CLPR_CONNECTOR_ALREADY_EXISTS` (556) - the commitment is already pending/used, or completion finds a Connector with the same `(channelId, connectorId)`.
- `CLPR_CONNECTOR_UNAUTHORIZED` (557) - the required Connector admin or stake-recipient key requirement cannot be established (for example, an unusable key or unresolved recipient account). A missing required signature instead fails with generic `INVALID_SIGNATURE`; the payer need not own either key if both required parties sign.
- `CLPR_INVALID_CONNECTOR_ADDRESS` (558) - defined for a missing/empty `connectorId`, but **not currently reachable**: `ClprCompleteConnectorHandler` validates `connectorId`'s length with the generic `INVALID_TRANSACTION_BODY` instead.
- `CLPR_INVALID_CONNECTOR_CONTRACT` (559) - the supplied `connectorContract` is missing, deleted, not a smart contract, or has no key that could consent to the binding. A contract with a key that did not sign fails with generic `INVALID_SIGNATURE`.
- `CLPR_INSUFFICIENT_STAKE` (560) - `lockedStake` is below the network's USD-denominated minimum, converted at the active exchange rate.
- `CLPR_CONNECTOR_HAS_IN_FLIGHT_MESSAGES` (567) - the Connector still has unacknowledged outbound Data Messages; all must reach a terminal reply before deregistration.

#### Outbound message dispatch (`sendMessage` - a system-contract call inside a `ContractCall`/`EthereumTransaction`, not a Connector lifecycle transaction)

These four are returned by `ClprServiceApiImpl.sendMessage` and the `sendMessage` system-contract call (`SendMessageCall`) when an application enqueues an outbound message through a Connector - not by `ClprSubmitBundleTransaction`, despite how adjacent this behavior is to bundle processing in the spec.

- `CLPR_QUEUE_FULL` (554) - the Channel's outbound message queue has reached `maxQueueDepth`.
- `CLPR_AUTHORIZATION_FAILED` (562) - the Connector doesn't exist or has no authorization contract, or that contract's `authorizeOutboundMessage` call reverted or returned false. Despite the similar name, this is a distinct, CLPR-specific code, not the generic `AUTHORIZATION_FAILED` a non-admin payer gets back from `ClprCloseChannelTransaction` (see the note above the Ledger configuration section) - the two situations are unrelated, so don't assume one from seeing the other.
- `CLPR_QUEUE_QUOTA_EXCEEDED` (564) - the Connector has exceeded its per-Channel queue quota (`connectorQueueQuotaPct`); other Connectors on the same Channel may still enqueue messages.
- `CLPR_INSUFFICIENT_CONNECTOR_BALANCE` (565) - defined for a Connector balance that can't cover the queue fee, including any congestion escalation, but **not currently reachable**: `sendMessage`'s outbound path only checks queue depth (`CLPR_QUEUE_FULL`) and the per-Connector quota (`CLPR_QUEUE_QUOTA_EXCEEDED`) - no balance/fee check exists there today. Don't confuse this with the unrelated, implemented `CONNECTOR_UNDERFUNDED` *reply status* (a different mechanism, checked against the receiving Connector's balance during inbound bundle dispatch, not this response code).

#### Peer endpoint eviction (no SDK wrapper)

- `CLPR_PEER_ENDPOINT_NOT_FOUND` (572) - returned by `ClprEvictPeerEndpoint` when the endpoint to evict is not in the Channel's cached endpoint manifest. Map it for wire compatibility; the SDK does not submit eviction transactions.

#### Internal

- `CLPR_INTERNAL_STATE_CORRUPTION` (566) - CLPR state is corrupt (e.g. an outbound message ID was assigned but the message doesn't exist in the queue). This should never happen in correct operation; treat it as a bug report, not a caller-input error, and surface it distinctly rather than folding it into ordinary validation-failure handling.

#### Transaction Retry

None of the codes above are transient/node-specific failures in the sense the SDK's existing retry loop targets (e.g. `BUSY`, `PLATFORM_TRANSACTION_NOT_CREATED`).
They are all deterministic validation outcomes based on Channel/Connector/bundle state and should **not** trigger automatic retry with the same transaction body.
`CLPR_RATE_LIMITED` is the one exception worth flagging *once it's actually implemented* (see the note above - it isn't yet): implementers should confirm with the CLPR working group whether it should be added to each SDK's default retryable-status set (analogous to existing throttle-related codes), since a `submitBundle` caller may need to retry the same bundle later once backlog clears.

The mirror node queries return no consensus-node response codes; their HTTP retry behavior is covered under [Mirror node query implementation](#mirror-node-query-implementation) below.

### Fees

CLPR fees follow the consensus node [fee design](https://github.com/hiero-ledger/hiero-consensus-node/blob/08036e992bd5db2feba155c11f7676778b861775/hedera-node/docs/design/services/clpr-service/config-and-slashing.md#fees-clprfeecalculator) on the `fix-clpr-fees` branch at 08036e99 ([#28137](https://github.com/hiero-ledger/hiero-consensus-node/pull/28137), open). That pull request describes its values as temporary until fees are confirmed. The fee *mechanisms* below are the selected Phase 2 behavior; the dollar amounts are illustrative and must not be hard-coded in SDK logic or acceptance assertions. The SDK computes no CLPR prices; it relies on the network's fee schedule and the standard max-fee and query-cost mechanisms. What matters to SDK users:

- **HAPI queries are paid.** `ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery` use the standard paid-query flow. Each quotes $0.01 plus 300,000 gas at the schedule's gas rate, covering the proof work.
- **Default max transaction fee.** The lifecycle transactions carry high service fees in the branch's mainnet schedule: $100 each for `ClprRegisterChannel` and `ClprCompleteChannel` (plus state bytes beyond 8,192), $10 for `ClprRegisterConnector` and $25 for `ClprCompleteConnector`. The SDK's ordinary default max transaction fee is too low for them. Each wrapper should set a default max fee large enough for the configured price, as the consensus node test clients do, and let callers override it. The amounts are governed fee-schedule values and may change; revisit each default against the final baseline's schedule.
- **Bundles.** `ClprSubmitBundle` is exempt from the node and network fee components. Its service fee covers the bundle bytes plus the verifier's measured gas, capped at 300,000 gas. A rejected bundle costs only the transaction fee.
- **Privileged transactions.** `ClprCloseChannel` and `ClprUpdateLedgerConfiguration` have a $0 service fee, and the remaining fees are waived for privileged payers.
- **System-contract calls are payable.** In the fee branch, `sendMessage` and `getChannelQueueState` are `payable`. Each call has a target price ($0.10 for `sendMessage`, $0.02 for `getChannelQueueState` and `getEndpointManifest`); the caller pays part of it as gas and must attach the remainder as value. `sendMessage` also pays a state-byte surcharge above 1,024 message bytes, and only a successful send is charged the attached remainder. Off-chain contract call queries use the ordinary query payment instead. Contract examples and ABI fixtures must use the payable signatures and attach value; see [Contract calls through existing SDK APIs](#contract-calls-through-existing-sdk-apis).
- **Connector stake.** The minimum `lockedStake` is set in USD and converted at the active exchange rate (see `ClprCompleteConnectorTransaction`).

### Mirror node query implementation

- **Transport.** Both queries go through the `Client`-owned `MirrorNodeHttpClient` with a `MirrorNodeRestPath`, as the [HTTP Transport Layer](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/proposals/http-transport-layer.md) proposal requires. Neither builds its own HTTP client, retry loop, or identity headers. Errors reach the caller in each query's own error type: `4xx` other than `429` is not retried; `429` / `5xx` follow `MirrorNodeHttpRetryPolicy`.
- **ID encoding.** 32-byte IDs in the equality filters are written as lowercase hex with a `0x` prefix, matching the mirror node design's examples.
- **Validation before the network call.** Every ID must be set and 32 bytes long.
- **Response mapping.**
  - Hex `0x...` strings map to `bytes`.
  - `seconds.nanoseconds` strings map to `dateTime`.
  - `0.0.x` strings map to `ContractId`.
  - `admin_key`'s `{_type, key}` maps to the SDK's `Key`, including `ProtobufEncoded` for key lists and threshold keys.
  - 64-bit integers must be parsed without precision loss, whether the design returns them as strings (`locked_stake`) or JSON numbers (the queue counters, `in_flight_message_count`, `slash_count`); convert stake to `Hbar` through its tinybar representation.
- **Single-row lookups.** Both routes identify at most one row. Read the first page only; a response with more than one row is an unexpected response error rather than a choice between rows.
- **Missing entities.** An empty result fails with a not-found error: an unknown Channel, or a Connector with no `ACTIVE` row. The Connector query sends `status=eq:ACTIVE` so retained `DELETED` rows are never reported as live Connectors. Because ingestion lags consensus, a not-found shortly after the creating transaction may be transient; callers wait and re-query rather than relying on a fixed delay.

## Test Plan

1. Given a fresh account, when it submits `ClprRegisterChannelTransaction` with a 32-byte `ownershipCommitment`, then the transaction succeeds.
   The receipt is the confirmation; the SDK deliberately offers no read of pending registrations (see [Mirror node queries](#mirror-node-queries)).
2. Given a `PENDING` commitment and a supported built-in or deployed verifier on both ledgers, when the same keypair submits `ClprCompleteChannelTransaction` on both ledgers with matching `channelId`, `publicKey`, and valid `signature`, then both transactions succeed and the Channel is `ACTIVE` on both ledgers.
3. Given a `PENDING` commitment, when an internal malformed-protobuf fixture for Channel completion carries a `signature` that does not verify against `publicKey`, then the transaction fails with `CLPR_INVALID_SIGNATURE`.
4. Given a `PENDING` commitment, when `ClprCompleteChannelTransaction` is submitted with a `channelId`/`publicKey` pair whose hash does not match the stored commitment, then the transaction fails with `CLPR_COMMITMENT_MISMATCH`.
5. Given an `ACTIVE` Channel and the network's Treasury or System Admin account as payer, when `ClprCloseChannelTransaction` is submitted, then the transaction succeeds and the Channel begins draining (no new locally-originated Data Messages).
6. Given an `ACTIVE` Channel, when `ClprCloseChannelTransaction` is submitted by a payer that is neither the Treasury nor System Admin account, then the transaction fails with `AUTHORIZATION_FAILED`.
7. Given an abandoned `PENDING` commitment (never completed) and the Treasury or System Admin account as payer, when `ClprCloseChannelTransaction` is submitted with the matching `ownershipCommitment`, then the transaction succeeds and that pending commitment is removed (no Channel identity was stored by registration).
8. Given an `ACTIVE` Channel, a valid bundle payload from a peer endpoint and a funded payer that is not a registered endpoint, when `ClprSubmitBundleTransaction` is submitted against the pinned CN baseline, then the transaction succeeds, the bundle is verified, and messages are dispatched. Revisit this expectation if CN changes the authority contract.
9. Given an `ACTIVE` Channel, when `ClprSubmitBundleTransaction` is submitted with a `bundlePayload` that fails verifier proof checks, then the transaction fails with `CLPR_BUNDLE_VERIFICATION_FAILED` and no Channel state changes.
10. Given an `ACTIVE` Channel, when `ClprSubmitBundleTransaction` is submitted with a bundle that makes no progress per the NoProgress check, then the transaction fails with `CLPR_NO_PROGRESS`.
11. Given an existing Channel and no prior commitment, when an account submits `ClprRegisterConnectorTransaction` with that 32-byte `channelId` and a valid 32-byte commitment, then the transaction succeeds; given a `channelId` with no Channel, then it fails with `CLPR_CHANNEL_NOT_FOUND`.
12. Given a pending Connector commitment, an existing Channel, a 32-byte salt, a deployed connector contract with a key, and a payer funding `lockedStake` at or above the network minimum, when `ClprCompleteConnectorTransaction` is submitted with a valid ownership signature and the connector contract's key signs, then the transaction succeeds and the Connector is created keyed by `(channelId, connectorId)`; when the contract's key does not sign, then it fails with `INVALID_SIGNATURE`; given a contract with no key, then it fails with `CLPR_INVALID_CONNECTOR_CONTRACT`.
13. Given a pending Connector commitment, when `ClprCompleteConnectorTransaction` is submitted with `lockedStake` below the network minimum, then the transaction fails with `CLPR_INSUFFICIENT_STAKE`.
14. Given an existing Connector with zero in-flight messages and its `adminKey`, when `ClprDeregisterConnectorTransaction` is submitted with a `stakeRecipient` that co-signs, then the transaction succeeds and `lockedStake` is transferred to `stakeRecipient`.
15. Given an existing Connector with at least one in-flight message, when `ClprDeregisterConnectorTransaction` is submitted, then the transaction fails with `CLPR_CONNECTOR_HAS_IN_FLIGHT_MESSAGES`.
16. Given the Treasury or System Admin account as payer, when `ClprUpdateLedgerConfigurationTransaction` is submitted with new `ClprThrottles` values, then `ClprGetLedgerConfigurationQuery` subsequently reflects the updated throttles and an unchanged `chainId`/`protocolVersion`.

18. Given the Treasury or System Admin account as payer, when an internal raw-protobuf update fixture bypasses SDK validation with `throttles.maxSyncBytes` less than `maxMessagePayloadBytes + 65,536`, then CN returns `INVALID_CLPR_CONFIGURATION`.
19. Given CLPR is enabled, a usable signed snapshot and successful configured sender-side proof validation, when either HAPI query is executed, then its proof is non-empty and preserved byte-for-byte. The configuration response may contain newer live values; the manifest/proof pair comes from the same snapshot.
20. Given no usable signed snapshot or a sender-side validation failure, when either HAPI query returns an empty proof, then the SDK preserves it without converting the successful response into an error or inventing proof material.
21. ### Ownership test vectors

## SDK Example

This example follows the "Setting up a new route" cross-role scenario: establishing a Channel between two Hiero networks and submitting a first bundle.

1. On Ledger A, select a supported built-in verifier or deploy/reuse a verifier for Ledger B's proof system; obtain its `ContractId`. Do the same on Ledger B for Ledger A's proof system.
2. Generate a keypair for the registrant and choose a 32-byte `channelId`. Obtain `ownershipCommitment` with `ClprRegisterChannelTransaction.computeOwnershipCommitment(channelId, publicKey)`; the helper handles the scheme-specific key encoding. For a Connector, use `ClprRegisterConnectorTransaction.computeConnectorId(channelId, publicKey, salt)` followed by `computeOwnershipCommitment(connectorId, publicKey)`, and register it with the same `channelId` once the Channel exists.
3. Submit `ClprRegisterChannelTransaction` with `ownershipCommitment` to Ledger A. Verify the transaction succeeds.
4. Submit the same `ClprRegisterChannelTransaction` (same commitment) to Ledger B. Verify the transaction succeeds.
5. Execute `ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery` against Ledger B; wait for non-empty `configurationStateProof` and `manifestStateProof` accepted by the selected verifier and retain the bytes unchanged for Ledger A (and vice versa). Do not infer proof contents from the live configuration fields returned alongside them.
6. Build `ClprCompleteChannelTransaction` for Ledger A with `channelId`, the verifier `ContractId` from step 1, `configProofBytes` = Ledger B's `configurationStateProof`, and `endpointManifestProofBytes` = Ledger B's `manifestStateProof`, then call `setOwnershipProof(privateKey)` last, using the same registrant keypair from step 2, because the signature covers all four fields. Submit it and verify the transaction succeeds.
7. Repeat step 6 symmetrically on Ledger B using Ledger A's proofs.
8. Once the mirror node CLPR REST API is deployed, on each ledger execute `MirrorNodeClprChannelQuery` with the `channelId` and verify that its status is `ACTIVE`, waiting for mirror node ingestion without assuming a fixed delay.
9. After registering/funding the route's Connectors and configuring the application callbacks, once an application contract enqueues a message through `sendMessage` and an endpoint relay observes it, verify that a subsequent `ClprSubmitBundleTransaction` submitted by that endpoint against either ledger succeeds. Confirm the intended application callback payload or state change; queue counters alone do not prove delivery.
