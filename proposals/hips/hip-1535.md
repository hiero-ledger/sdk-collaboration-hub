# HIP-1535: CLPR - A Cross Ledger Protocol for Hiero

## Summary

This proposal adds SDK support for **CLPR** ("Clipper"), the Cross Ledger Protocol defined by [HIP-1535](https://github.com/hiero-ledger/hiero-improvement-proposals/blob/4f5da41a527ad6b3a52f5b6d8f39e31565426035/HIP/hip-1535.md). It defines typed HAPI transactions and queries, ownership-proof helpers, response models and compatibility tests.

**HAPI contract:** the API definitions and handler behavior use consensus node [76ba2903](https://github.com/hiero-ledger/hiero-consensus-node/tree/76ba2903da9e9464bdc30149eb931d768ff0fa00/hedera-node/hedera-clpr-service-impl/src/main/java/com/hedera/node/app/service/clpr/impl/handlers), including [`ClprService`](https://github.com/hiero-ledger/hiero-consensus-node/blob/76ba2903da9e9464bdc30149eb931d768ff0fa00/hapi/hedera-protobuf-java-api/src/main/proto/services/clpr_service.proto). The service exposes eight transactions and two queries. It has no `redactMessage` RPC.

The proposal also defines two mirror node queries for Channel and Connector state using the [CLPR REST design](https://github.com/hiero-ledger/hiero-mirror-node/blob/71740540ed0fabf2dfaf1545caf150e7c7f227c2/docs/design/clpr.md#rest-api-implementation) and the [HTTP Transport Layer](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/proposals/http-transport-layer.md) proposal. These queries are follow-up scope and require agreement on the REST contract and endpoint availability. Endpoint sync, node publication/maintenance, verifier implementations and application contracts are outside the SDK implementation.

## New APIs

New types follow the existing SDK conventions for native-service transactions (e.g. `TopicCreateTransaction`) and queries (e.g. `AccountInfoQuery`).
Fixed-length byte fields are represented as `bytes` per the [API Guidelines](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/guides/api-guideline.md) - SDKs should validate the documented fixed lengths client-side before submission where practical.
Setters/getters are the standard per-field accessors and are omitted below. Transaction and query builders are mutable until frozen/executed; response and value fields are immutable.
None of the eight transaction bodies is present in the pinned `SchedulableTransactionBody`; reject `schedule()` locally for all eight rather than serializing an unsupported scheduled body.

### ClprSignatureScheme

```text
enum ClprSignatureScheme {
    ECDSA_SECP256K1
    ED25519
}
```

**Purpose:** identifies which signing scheme a commit-reveal proof used, so the consensus node knows how to verify the accompanying `publicKey`/`signature` pair.

Key/signature encoding for the commit-reveal proofs below.
`ECDSA_SECP256K1` (default) uses a 64-byte uncompressed public key (`x || y`, no `0x04` prefix) and a 64-byte `r || s` signature.
`ED25519` uses a 32-byte public key and a 64-byte signature.
This is still a wire-level field on every commit-reveal proof, but SDKs should not expose it as an independently settable value, to avoid a caller supplying a scheme/key/signature combination that doesn't actually match - see the `setOwnershipProof` methods on `ClprCompleteChannelTransaction`/`ClprCompleteConnectorTransaction` below, which derive it automatically rather than accepting it as a separate, possibly-inconsistent input.

### ClprRegisterChannelTransaction

**Purpose:** begins establishing a new cross-ledger Channel by staking a claim on a Channel ID without revealing it, so no one else can race to claim the same ID first.

Phase 1 (Commit) of the two-phase channel-establishment scheme. Permissionless - any payer may submit. Duplicate commitments fail with `CLPR_CHANNEL_ALREADY_EXISTS`; a completed commitment remains registered, including after closure.

```text
ClprRegisterChannelTransaction extends Transaction {
    @@nullable ownershipCommitment: bytes

    @@static
    bytes computeOwnershipCommitment(channelId: bytes, publicKey: PublicKey)
}
```

- `ownershipCommitment` - 32-byte `keccak256(channel_id || public_key)`. Reveals neither value, preventing a cross-ledger front-runner from claiming the same Channel ID before the registrant reveals it.
- `computeOwnershipCommitment` - proposed helper accepting a 32-byte Channel ID and an SDK `PublicKey`. Derive the scheme from the key and use the canonical encoding above, including decompression to 64-byte `x || y` for secp256k1. Do not concatenate JS `PublicKey.toBytesRaw()` directly: its secp256k1 output is compressed. Reject unsupported key types and invalid ID lengths locally; do not mutate a transaction.

### ClprCompleteChannelTransaction

**Purpose:** finishes establishing a Channel by revealing the committed identity and activating it, so cross-ledger messaging can begin.

Phase 2 (Reveal). Verifies the commitment preimage and signature, authenticates the peer's configuration via the named verifier contract, and activates the Channel.

```text
ClprCompleteChannelTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable verifierContract: ContractId
    @@nullable configProofBytes: bytes
    @@nullable endpointManifestProofBytes: bytes

    ClprCompleteChannelTransaction setOwnershipProof(privateKey: PrivateKey)
    @@nullable bytes getPublicKey()
    @@nullable bytes getSignature()
    @@nullable ClprSignatureScheme getSignatureScheme()
}
```

- `channelId` - 32 bytes, identical value used in `registerChannel`, identical on both ledgers.
- `setOwnershipProof` - proposed SDK convenience: require `channelId` first, derive `publicKey` and `signatureScheme` from the key, and sign the raw 32-byte `keccak256(channelId)` digest. With the current JS/Java/Go `PrivateKey.sign()` APIs, pass `channelId` for ECDSA because that API already applies keccak256; pass `keccak256(channelId)` for Ed25519 because that API signs its input bytes directly. A raw-digest ECDSA primitive instead receives the digest. Do not hash twice or apply a message prefix. Use the same public-key encoding as the commitment; do not retain the private key.
- Proof getters are nullable and return the stored wire values, including after `Transaction.fromBytes()`, without requiring a private key. A missing or invalidated proof returns null; when present, derive the scheme from the helper or decode it from the wire, including the protobuf ECDSA default. Changing `channelId` clears all three proof values. Freezing/executing without a complete proof fails locally; an unchanged decoded proof may be re-serialized without rebuilding it. There are no independent setters for these proof fields.
- `verifierContract` - the `ContractId` of a supported built-in verifier (currently system addresses `0x16e` through `0x171`) or a deployed verifier contract; immutable for the Channel's lifetime.
- `configProofBytes` - opaque proof passed to the verifier's `verifyConfig` to authenticate the peer's `ClprLedgerConfiguration` (which carries the peer's initial trust anchor).
- `endpointManifestProofBytes` - opaque proof attesting the peer's initial `ClprEndpointManifest`. An empty endpoint list is valid, but this does not imply empty proof bytes are valid: the Hiero TSS verifier rejects them. Other verifier families may support a synthesized bring-up manifest. Callers must supply the proof encoding accepted by the selected verifier.

### ClprCloseChannelTransaction

**Purpose:** shuts down a Channel (or cleans up an abandoned registration) so it stops accepting new outbound messages.

Requires the network's **Treasury or System Admin account** - the same superuser privilege that gates freeze, software-update, and fee-schedule transactions (`PrivilegesVerifier.checkClprAdmin` simply calls the existing `isSuperUser` check).
There is no separate, delegatable CLPR-specific admin key or role, despite the "CLPR Service Admin" terminology used elsewhere.
This same authorization gates `ClprUpdateLedgerConfigurationTransaction` below. Registration/completion and the pinned bundle handler are permissionless; Connector deregistration has its own required signatures.
Closing an `ACTIVE` or `PAUSED` Channel enters `CLOSING`, or `DRAINED` if its queue is already acknowledged. Closing a `DRAINED` Channel transitions it to `CLOSED`. It can also delete an abandoned `PENDING` commitment that was never completed.

```text
ClprCloseChannelTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable ownershipCommitment: bytes
}
```

- `ownershipCommitment` - only required/used when no Channel exists yet for `channelId` (sweeping an abandoned `registerChannel` commitment); ignored when an active Channel record is found.

### ClprSubmitBundleTransaction

**Purpose:** delivers a batch of cross-ledger messages, plus the state proof authenticating them, from a peer ledger's endpoint into this ledger's CLPR Service.

Submits a bundle of messages synced from a peer ledger's endpoint. The pinned implementation permits any payer under its default API permissions: ingest checks CLPR enablement and `preHandle` adds no endpoint-identity requirement. The no-progress penalty path charges the payer; permissionless submission does not imply fee-free or penalty-free submission.

```text
ClprSubmitBundleTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable bundlePayload: bytes
}
```

- `bundlePayload` - opaque to the SDK and to the protocol; interpreted only by the Channel's verifier contract.
The wire format also carries deprecated `endpointNodeId`/`endpointSignature` fields that the pinned handler ignores; do not expose them as SDK setters or imply they authenticate the caller. The proto describes address-book endpoint authority, but the handler does not enforce it and the mirror node design assumes permissionless submission. CN must confirm the intended authority contract; endpoint-only submission remains an open requirement, not current enforced behavior. The SDK wrapper adds no relay/discovery behavior.

### ClprRegisterConnectorTransaction

**Purpose:** begins registering a Connector - the economic actor that will authorize and pay for cross-ledger message execution - by staking a claim on its identity without revealing it.

Phase 1 (Commit) for Connector registration. Permissionless. Duplicate commitments fail with `CLPR_CONNECTOR_ALREADY_EXISTS`; commitments remain registered after completion and deregistration, so reuse is rejected.

```text
ClprRegisterConnectorTransaction extends Transaction {
    @@nullable commitment: bytes

    @@static
    bytes computeConnectorId(channelId: bytes, publicKey: PublicKey, salt: bytes)
    @@static
    bytes computeOwnershipCommitment(connectorId: bytes, publicKey: PublicKey)
}
```

- `commitment` - 32-byte `keccak256(connectorId || publicKey)`, where `connectorId = keccak256(channelId || publicKey || salt)`.
- `computeConnectorId` and `computeOwnershipCommitment` - proposed helpers applying those formulas with the same canonical `PublicKey` encoding as the Channel helper. Require 32-byte IDs and salt and reject unsupported keys locally. Call the ID helper first, then the commitment helper; neither signs, retains a private key or mutates a transaction.

### ClprCompleteConnectorTransaction

**Purpose:** finishes registering a Connector by revealing its identity, posting its slashable stake, and activating it to authorize and pay for messages.

Phase 2 (Reveal). Requires an existing Channel. Creates the Connector, keyed by `(channelId, connectorId)`, once the derived ID, commitment preimage and signature are verified; the payer funds the locked stake.

```text
ClprCompleteConnectorTransaction extends Transaction {
    @@nullable connectorId: bytes
    @@nullable salt: bytes
    @@nullable channelId: bytes
    @@nullable connectorContract: ContractId
    @@nullable adminKey: Key
    lockedStake: Hbar

    ClprCompleteConnectorTransaction setOwnershipProof(privateKey: PrivateKey)
    @@nullable bytes getPublicKey()
    @@nullable bytes getSignature()
    @@nullable ClprSignatureScheme getSignatureScheme()
}
```

- `connectorId` - exactly 32 bytes, re-derived by the handler as `keccak256(channelId || publicKey || salt)`.
- `salt` - exactly 32 bytes; all-zero is valid for a single Connector.
- `setOwnershipProof` - proposed SDK convenience with the same key/signature encoding as Channel completion. Require `channelId`, `connectorId` and `salt` first; validate the derived Connector ID, then sign `keccak256(connectorId || clprServiceAddress)`, where the service address is the 20 bytes `0x000000000000000000000000000000000000016e`. For the current SDK `PrivateKey.sign()` APIs, pass the unhashed `connectorId || clprServiceAddress` to ECDSA and its keccak256 digest to Ed25519. Changing any of the three bound fields clears the proof. The nullable getters and `Transaction.fromBytes()` behavior match Channel completion; freezing/executing requires a complete proof. Do not retain the private key or expose independent setters for its three proof fields.
- `connectorContract` - the local authorization contract governing message dispatch for this Connector; must refer to an already-deployed contract.
- `adminKey` - required; authorizes future `deregisterConnector`. Uses the SDK's existing `Key` abstraction (any key type/threshold key supported elsewhere).
- `lockedStake` - slashable `Hbar` bond, encoded as unsigned tinybars on the wire. Use the portable `Hbar` range of 0 through 2^63-1 tinybars and reject negative values, fractions of a tinybar or unrepresentable amounts before serialization; it must meet the network's configured minimum or the transaction fails with `CLPR_INSUFFICIENT_STAKE`.

### ClprDeregisterConnectorTransaction

**Purpose:** retires a Connector that's no longer needed and returns its locked stake to a designated recipient.

Requires the Connector's `adminKey` to sign. Removes the Connector and returns its locked stake.

```text
ClprDeregisterConnectorTransaction extends Transaction {
    @@nullable channelId: bytes
    @@nullable connectorId: bytes
    @@nullable stakeRecipient: AccountId
}
```

- `stakeRecipient` - must be explicitly specified and must itself sign the transaction (in addition to the Connector's `adminKey`).

### ClprUpdateLedgerConfigurationTransaction

**Purpose:** lets the network admin adjust this ledger's CLPR capacity limits (`ClprThrottles`) after genesis.

Requires the network's Treasury or System Admin account (see `ClprCloseChannelTransaction` above).
Updates the local ledger's throttle configuration by replacing the entire throttles object, not patching individual fields. Read the current values with `ClprGetLedgerConfigurationQuery`, construct a new `ClprThrottles` with the desired changes and all seven values, then submit it. The SDK serializes only `configuration.throttles`; it does not expose setters for genesis/server-owned fields.
`chainId`, `protocolVersion`, and `timestamp` on the supplied configuration are ignored by the handler - the first two are immutable (set at genesis), and the timestamp is stamped automatically.

`ClprThrottles` fields are validated before acceptance.
`maxMessagesPerBundle`, `maxMessagePayloadBytes`, `maxQueueDepth`, `maxGasPerMessage`, and `maxSyncBytes` must all be strictly positive (`0` fails with `INVALID_CLPR_CONFIGURATION`); `maxLocalEndpoints`/`maxPeerEndpoints` are the exception, where `0` means "no limit."
The handler also enforces a deadlock guard: `maxSyncBytes` must be at least `maxMessagePayloadBytes + 65,536` bytes, so a bundle carrying one max-sized message always has room for its proof/envelope overhead.
Without this floor a Channel could be configured into a permanent stall, since the sender could never assemble a bundle that fits, the peer would never acknowledge, and the queue would never drain.

```text
ClprUpdateLedgerConfigurationTransaction extends Transaction {
    @@nullable throttles: ClprThrottles
}
```

### ClprThrottles

**Purpose:** the set of capacity limits a ledger enforces on its CLPR Service - message size, bundle size, queue depth, and endpoint counts.

```text
ClprThrottles {
    @@immutable maxMessagesPerBundle: uint32
    @@immutable maxMessagePayloadBytes: uint32
    @@immutable maxGasPerMessage: uint64
    @@immutable maxQueueDepth: uint32
    @@immutable maxSyncBytes: uint64
    @@immutable maxLocalEndpoints: uint32
    @@immutable maxPeerEndpoints: uint32

    @@static
    ClprThrottles of(
        maxMessagesPerBundle: uint32,
        maxMessagePayloadBytes: uint32,
        maxGasPerMessage: uint64,
        maxQueueDepth: uint32,
        maxSyncBytes: uint64,
        maxLocalEndpoints: uint32,
        maxPeerEndpoints: uint32
    )
}
```

Capacity limits advertised by a ledger's CLPR Service. The proposed factory requires every field and validates the positive-value and `maxSyncBytes` floor rules above; zero endpoint limits remain valid. Language-specific constructors may provide the equivalent operation. Immutable fields do not imply an output-only type.

### ClprGetLedgerConfigurationQuery

**Purpose:** reads a ledger's current CLPR configuration, typically to obtain the state proof material needed to establish a Channel with it.

```text
ClprGetLedgerConfigurationQuery extends Query<ClprLedgerConfigurationInfo> {
}
```

Free public read when CLPR is enabled; no payment or admin authorization is required. Takes no CLPR-specific parameters beyond the standard query header.

### ClprLedgerConfigurationInfo

**Purpose:** the response payload for `ClprGetLedgerConfigurationQuery`.

```text
ClprLedgerConfigurationInfo {
    @@immutable protocolVersion: uint32
    @@immutable chainId: string
    @@immutable serviceAddress: bytes
    @@immutable timestamp: dateTime
    @@immutable throttles: ClprThrottles
    @@immutable initialTrustAnchor: bytes
    @@immutable initialTrustAnchorId: bytes
    @@immutable configurationStateProof: bytes
}
```

- `chainId` - CAIP-2 identifier (e.g. `hedera:mainnet`, `eip155:1`).
- `configurationStateProof` - opaque serialized state proof from a signed snapshot; pass it unchanged as `configProofBytes` only when the peer verifier accepts that encoding. The pinned handler returns live configuration fields alongside a snapshot proof, so the SDK must not claim the proof authenticates those exact live values. It may be empty when no usable snapshot exists or configured sender-side proof validation fails. Preserve an empty proof as a successful read with unavailable proof material; applications needing proof should re-query with bounded retry.

### ClprGetEndpointManifestQuery

**Purpose:** reads a ledger's current set of CLPR relay endpoints, used to seed or recover a Channel's peer endpoint cache.

```text
ClprGetEndpointManifestQuery extends Query<ClprEndpointManifestInfo> {
}
```

Free public read when CLPR is enabled - no payment or admin authorization required.
With a usable signed snapshot, returns its endpoint manifest and matching proof, used both to seed a new Channel's peer manifest and to construct manifest-recovery bundles; do not assume this is the newest live manifest.

### ClprEndpointManifestInfo

**Purpose:** the response payload for `ClprGetEndpointManifestQuery`.

```text
ClprEndpointManifestInfo {
    @@immutable version: uint64
    @@immutable serviceAddress: bytes
    @@immutable endpoints: list<ClprEndpoint>
    @@immutable manifestStateProof: bytes
}
```

- `manifestStateProof` - opaque bytes to preserve unchanged. As with `configurationStateProof`, it may be empty before a usable signed snapshot or after configured sender-side validation rejects a proof. An empty proof does not mean the endpoint list is empty and must not be submitted to a verifier that requires proof.

### ClprEndpoint

**Purpose:** describes one CLPR relay endpoint - its network address, TLS identity, and owning account - as it appears in an endpoint manifest.

```text
ClprEndpoint {
    @@immutable serviceEndpoint: ClprServiceEndpoint
    @@immutable tlsCertificate: bytes
    @@immutable accountId: bytes
}
```

### ClprServiceEndpoint

**Purpose:** the network address (IP and port) of a single CLPR endpoint.

```text
ClprServiceEndpoint {
    @@immutable ipAddress: string
    @@immutable port: uint32
}
```

Numeric IPv4/IPv6 address only - no DNS hostnames, consistent with the SDK's existing `Endpoint`/node-address-book representations elsewhere.

### Mirror node queries

Channel and Connector state is read from the mirror node rather than the consensus node, since the mirror node is what indexes this state; smart contracts can use the separate `getChannel` system-contract view for on-chain decisions.
This proposal adds only the two reads SDK users need: a Channel's current state and a Connector's current state, each looked up by ID.
Both follow the established mirror node query pattern (`MirrorNodeAccountBalanceQuery`) and the [HTTP Transport Layer](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/proposals/http-transport-layer.md) proposal:

- Each is a standalone class; neither extends `Query`.
- They are free, and eventually consistent: allow for mirror node ingestion lag; no latency bound is established here.

Ledger configuration and the endpoint manifest stay on `ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery` above, because only the consensus node can produce the state proofs they return.

| Question                                                                                                 | Query                                                                 |
|------------------------------------------------------------------------------------------------------- |------------------------------------------------------------------------|
| Is my Channel still `ACTIVE`, or has it moved to `PAUSED`, `CLOSING` or `CLOSED`?                        | `MirrorNodeClprChannelQuery`                                          |
| Is my Channel still configured the way I vetted it: same verifier, verifier fingerprint and peer chain?  | `MirrorNodeClprChannelQuery`                                          |
| Is the Channel's outbound queue draining?                                                                | `MirrorNodeClprChannelQuery`                                          |
| How much stake does my Connector have locked, and has it been slashed?                                   | `MirrorNodeClprConnectorQuery`                                        |
| How many of my Connector's messages are still in flight? Deregistration is blocked until none are.       | `MirrorNodeClprConnectorQuery`                                        |
| What can my Connector still spend on execution?                                                          | Existing `MirrorNodeAccountBalanceQuery` on its `connectorContractId` |

These are what the [CLPR spec](https://github.com/LFDT-CLPR/clpr-spec/blob/945082d69e65dd0fd9e9bdf8d59cb8121579f6fd/clpr-service.md) (§4.2) asks application developers to monitor: "Connector health (balance declining, slashing events)" and "Channel status changes (PAUSED, CLOSING, CLOSED)".

Deliberately not included:

- **Chain or Channel discovery.** The spec tells applications to treat `channel_id` and `connector_id` as configured values, and anyone can claim any chain ID. The SDK therefore offers no "find Channels for a chain" query.
- **Pending registrations.** The `ClprRegisterChannelTransaction` receipt confirms a registration.
- **Message history.** Applications learn each message's outcome on-chain, through their `onClprResponse` callback. Message history is an auditing feature, served by the mirror node REST API and the explorer.

### MirrorNodeClprChannelQuery

**Purpose:** reads one Channel's current state, so an application can confirm the Channel is healthy and still configured the way it was vetted.

```text
MirrorNodeClprChannelQuery {
    @@nullable channelId: bytes

    @@async
    MirrorNodeClprChannel execute(client: Client)
}
```

**Proposed route, pending mirror node agreement:** `GET /api/v1/clpr/channels?channel.id=eq:{channelId}`. `channelId` is required and must be 32 bytes; `execute` fails before any network call otherwise. Use the matching row from the filtered list, following `links.next` until found or exhausted.

### MirrorNodeClprChannel

**Purpose:** a Channel's current state as recorded by the mirror node.

```text
@@finalType
MirrorNodeClprChannel {
    @@immutable channelId: bytes
    @@immutable chainId: string
    @@immutable status: ClprChannelStatus
    @@immutable verifierContractId: ContractId
    @@immutable verifierFingerprint: bytes
    @@immutable trustAnchorId: bytes
    @@immutable nextMessageId: uint64
    @@immutable ackedMessageId: uint64
    @@immutable receivedMessageId: uint64
    @@immutable createdTimestamp: dateTime
    @@immutable modifiedTimestamp: dateTime
}
```

- `chainId` - the peer chain the Channel claims to reach. Anyone can claim any chain ID, so treat it as a check against the application's own configuration, not as proof of the peer's identity.
- `verifierFingerprint` - a fixed identity hash for a built-in verifier, or the keccak256 hash of a deployed verifier's bytecode, for comparison with the value the application vetted. A proxy's bytecode doesn't change when its logic is upgraded, so the fingerprint alone won't reveal an upgrade behind a proxy.
- `nextMessageId`, `ackedMessageId`, `receivedMessageId` - queue positions. The outbound backlog is `nextMessageId - 1 - ackedMessageId`. A backlog that keeps growing while the Channel is `ACTIVE` suggests the peer has stopped acknowledging.
- `modifiedTimestamp` - proposed mapping from the REST state range's `timestamp.from`, when the current state took effect. The current mirror node design has no field named `modified_timestamp`; confirm this mapping with that team.

### ClprChannelStatus

**Purpose:** a Channel's lifecycle state.

```text
enum ClprChannelStatus {
    ACTIVE
    PAUSED
    CLOSING
    DRAINED
    CLOSED
}
```

The proto also defines `PENDING`, but the mirror node never returns it: a Channel record exists only once the Channel is completed.

### MirrorNodeClprConnectorQuery

**Purpose:** reads one Connector's current state, so its operator, or an application relying on it, can monitor stake, slashing and in-flight messages.

```text
MirrorNodeClprConnectorQuery {
    @@nullable channelId: bytes
    @@nullable connectorId: bytes

    @@async
    MirrorNodeClprConnector execute(client: Client)
}
```

**Proposed route, pending mirror node agreement:** `GET /api/v1/clpr/connectors?channel.id=eq:{channelId}&connector.id=eq:{connectorId}&deleted=eq:false`. Both IDs are required and must be 32 bytes; `execute` fails before any network call otherwise. Use the matching live row from the filtered list, following `links.next` until found or exhausted.

### MirrorNodeClprConnector

**Purpose:** a Connector's current state as recorded by the mirror node.

```text
@@finalType
MirrorNodeClprConnector {
    @@immutable connectorId: bytes
    @@immutable channelId: bytes
    @@immutable connectorContractId: ContractId
    @@immutable adminKey: Key
    @@immutable lockedStake: Hbar
    @@immutable inFlightMessageCount: uint64
    @@immutable slashCount: uint64
    @@immutable createdTimestamp: dateTime
}
```

- `lockedStake` - the remaining slashable `Hbar` stake, decoded losslessly from the REST tinybar integer; reject values outside the portable `Hbar` range rather than wrapping or truncating them. Each slash reduces it.
- `slashCount` - reaching the configured `slashBanThreshold` bans/removes the Connector; the CN default at the source baseline is five, not a fixed protocol constant.
- `inFlightMessageCount` - `ClprDeregisterConnectorTransaction` fails with `CLPR_CONNECTOR_HAS_IN_FLIGHT_MESSAGES` until this reaches zero.
- The Connector's spendable balance is the HBAR balance of `connectorContractId`, which the existing `MirrorNodeAccountBalanceQuery` already returns.

### Mirror node dependencies

The mirror node design defines five REST routes: Channels, messages per Channel, pending Channels, pending Connectors, and Connectors. Its Channel and Connector lists support known-ID filters without a chain-ID input. The SDK queries use these lists and require agreement on the following behavior before implementation.

1. **Filtered reads:** match the requested IDs, exclude deleted Connectors and exhaust `links.next` before reporting not found, allowing for ingestion lag.
2. **Fields and ingestion:** expose verifier fingerprint, trust-anchor ID and all three queue counters in the Channel response. Integration tests must cover outbound `sendMessage` ingestion, Connector changes during bundle processing (including slashes and bans), and contract-ID resolution.
3. **Response mapping agreement:** Channel responses use `timestamp: {from, to}`; confirm `modifiedTimestamp = timestamp.from`. Connector lists include deleted rows unless filtered, so a current-Connector query must exclude them and exhaust pagination before reporting not found.
4. **Bundle-authority discrepancy:** current CN handling and the mirror node design both permit ordinary payers to submit bundles, while HAPI prose describes endpoint authority. Obtain CN confirmation of the intended contract and track any future enforcement change; do not describe the prose restriction as already implemented.

The mirror node monitor's typed-transaction tests depend on Java SDK CLPR support (or a raw-protobuf workaround). That is a monitor-test dependency, not a prerequisite for every importer/REST implementation task.

## Internal Changes

### Response Codes

Import all **33** CLPR-related values in the pinned [HAPI response enum](https://github.com/hiero-ledger/hiero-consensus-node/blob/76ba2903da9e9464bdc30149eb931d768ff0fa00/hapi/hedera-protobuf-java-api/src/main/proto/services/response_code.proto), including retained/deprecated values, into SDK status enums and wire conversions. Grouping below describes current handler behavior separately from inactive wire definitions. `CLPR_MESSAGE_NOT_FOUND` remains defined even though the redaction RPC is absent; the other former redaction statuses are absent from this baseline.

A privileged-authority failure (e.g. a non-admin account submitting `ClprCloseChannelTransaction`) surfaces as the standard, pre-existing `AUTHORIZATION_FAILED` code, not a new CLPR-specific code, since CLPR admin checks route through the same `PrivilegesVerifier` path as other privileged transactions (e.g. system-file updates). Don't confuse this with `CLPR_AUTHORIZATION_FAILED` (562) below, a distinct, CLPR-specific code for an unrelated failure - the similar names are a real risk for mix-ups in error-handling code.

#### Ledger configuration (`ClprUpdateLedgerConfigurationTransaction`)

- `CLPR_NOT_ENABLED` (537) - the CLPR service is not enabled on this ledger (`clpr.enabled=false`); returned by every CLPR transaction and query, not just this one.
- `INVALID_CLPR_CONFIGURATION` (538) - a supplied throttle value is invalid, e.g. `maxMessagesPerBundle`, `maxMessagePayloadBytes`, or `maxQueueDepth` is not strictly positive, or the `maxSyncBytes` deadlock-guard floor (`maxMessagePayloadBytes + 65,536`) isn't met.
- `CLPR_CHAIN_ID_IMMUTABLE` (539) - defined for an attempt to change `chainId`, but **not currently reachable**: the handler doesn't throw it at all. It silently keeps the existing `chainId` and discards whatever value was submitted (see Test Plan #17). Confirm with the working group whether active rejection is actually intended, since the wire-level code exists but isn't wired up.
- `CLPR_TOO_MANY_SEED_ENDPOINTS` (540) - retained wire definition; no active throw path in the pinned update handler, which no longer updates the deprecated seed-endpoint list.
- `CLPR_INVALID_SEED_ENDPOINT` (541) - retained wire definition; no active throw path in the pinned update handler.

#### Channel lifecycle (`ClprRegisterChannelTransaction` / `ClprCompleteChannelTransaction` / `ClprCloseChannelTransaction`)

- `CLPR_CHANNEL_ALREADY_EXISTS` (542) - the commitment was already registered, or completion conflicts with a Channel that cannot be completed in its current state.
- `CLPR_INVALID_SIGNATURE` (543) - the reveal-phase signature doesn't verify against the supplied public key. Also returned by `ClprCompleteConnectorTransaction` for the same reason.
- `CLPR_INVALID_VERIFIER_CONTRACT` (544) - the supplied verifier is neither a supported built-in nor a valid deployed smart contract.
- `CLPR_VERIFIER_CONFIG_FAILED` (545) - the verifier contract's `verifyConfig` call failed or returned invalid data.
- `CLPR_COMMITMENT_MISMATCH` (546) - `keccak256(channelId || publicKey)` doesn't match any stored commitment. Also returned by `ClprCompleteConnectorTransaction` for the equivalent connector-commitment check.
- `CLPR_CHANNEL_NOT_FOUND` (547) - the specified `channelId` doesn't correspond to any known Channel.
- `CLPR_INVALID_CHANNEL_STATUS` (548) - the Channel's current status doesn't allow the requested transition (e.g. closing an already-`CLOSING`/`CLOSED` Channel).

#### Retained message status

- `CLPR_MESSAGE_NOT_FOUND` (549) - retained in the wire enum; no active throw path in the pinned handlers. Map it without requiring a redaction API or a live negative test.

#### Bundle submission and message dispatch (`ClprSubmitBundleTransaction`)

- `CLPR_INVALID_ENDPOINT_SIGNATURE` (551) - retained wire definition; no active throw path in the pinned bundle handler. The deprecated signature field is ignored, so do not document an active signature-validation check.
- `CLPR_BUNDLE_VERIFICATION_FAILED` (552) - the Channel's verifier contract rejected the bundle's state proof.
- `CLPR_RUNNING_HASH_MISMATCH` (553) - the bundle's running hash doesn't match the Channel's expected value.
- `CLPR_PAYLOAD_TOO_LARGE` (561) - the raw bundle exceeds local `maxSyncBytes`, or an inbound message exceeds local `maxMessagePayloadBytes`. Also returned outbound from `sendMessage` against the peer's advertised payload limit.
- `CLPR_BUNDLE_DECODE_FAILED` (568) - a per-message protobuf decode failed *inside a verifier-accepted bundle*. Since the verifier already attested to the bundle's contents, this specifically means the verifier signed off on malformed data - a stronger signal than an ordinary input-validation failure, since it implies a bug or compromise in the Channel's verifier rather than just a bad caller input. Processing stops. The handler writes `PAUSED` before throwing, but the transaction dispatcher rolls back on that exception without a replay callback. Persisted pause is therefore an unresolved CN behavior, not an SDK guarantee; obtain CN confirmation and integration evidence before asserting it.
- `CLPR_EMPTY_BUNDLE` (569) - **deprecated**, superseded by `CLPR_NO_PROGRESS` below. SDKs should recognize both for wire compatibility with older/newer nodes but should not document this one as the primary code.
- `CLPR_RATE_LIMITED` (570) - defined for an endpoint that exceeds its fair share of the ledger's bundle-submission throttle (`max_bundles_per_sec / num_registered_endpoints`), per its protobuf doc comment, but **not currently reachable**: no per-endpoint throttle-sharing check exists anywhere in `ClprSubmitBundleHandler` today. Treat the formula as the documented intent, not current behavior, until that check is implemented. See the Transaction Retry note below for the implication once it is.
- `CLPR_NO_PROGRESS` (571) - the bundle satisfies none of the **five** Bundle Progress Criteria the handler actually checks: new messages, trust-anchor advancement, ack progress, a Channel status transition (e.g. `CLOSING` -> `DRAINED`), or endpoint-manifest advancement; the no-progress path normally penalizes the submitting payer. The pinned handler also returns this status without that penalty for claimed ack advancement with no next reply; do not promise a penalty for every occurrence.

#### Connector lifecycle (`ClprRegisterConnectorTransaction` / `ClprCompleteConnectorTransaction` / `ClprDeregisterConnectorTransaction`)

- `CLPR_CONNECTOR_NOT_FOUND` (555) - the specified Connector doesn't exist.
- `CLPR_CONNECTOR_ALREADY_EXISTS` (556) - the commitment is already pending/used, or completion finds a Connector with the same `(channelId, connectorId)`.
- `CLPR_CONNECTOR_UNAUTHORIZED` (557) - the required Connector admin or stake-recipient key requirement cannot be established (for example, an unusable key or unresolved recipient account). A missing required signature instead fails with generic `INVALID_SIGNATURE`; the payer need not own either key if both required parties sign.
- `CLPR_INVALID_CONNECTOR_ADDRESS` (558) - defined for a missing/empty `connectorId`, but **not currently reachable**: `ClprCompleteConnectorHandler` validates `connectorId`'s length with the generic `INVALID_TRANSACTION_BODY` instead.
- `CLPR_INVALID_CONNECTOR_CONTRACT` (559) - the supplied `connectorContract` doesn't refer to a deployed smart contract.
- `CLPR_INSUFFICIENT_STAKE` (560) - `lockedStake` is below the network's configured minimum.
- `CLPR_CONNECTOR_HAS_IN_FLIGHT_MESSAGES` (567) - the Connector still has unacknowledged outbound Data Messages; all must reach a terminal reply before deregistration.

#### Outbound message dispatch (`sendMessage` - a system-contract call inside a `ContractCall`/`EthereumTransaction`, not a Connector lifecycle transaction)

These four are returned by `ClprServiceApiImpl.sendMessage` and the `sendMessage` system-contract call (`SendMessageCall`) when an application enqueues an outbound message through a Connector - not by `ClprSubmitBundleTransaction`, despite how adjacent this behavior is to bundle processing in the spec.

- `CLPR_QUEUE_FULL` (554) - the Channel's outbound message queue has reached `maxQueueDepth`.
- `CLPR_AUTHORIZATION_FAILED` (562) - the Connector doesn't exist or has no authorization contract, or that contract's `authorizeOutboundMessage` call reverted or returned false. Despite the similar name, this is a distinct, CLPR-specific code, not the generic `AUTHORIZATION_FAILED` a non-admin payer gets back from `ClprCloseChannelTransaction` (see the note above the Ledger configuration section) - the two situations are unrelated, so don't assume one from seeing the other.
- `CLPR_QUEUE_QUOTA_EXCEEDED` (564) - the Connector has exceeded its per-Channel queue quota (`connectorQueueQuotaPct`); other Connectors on the same Channel may still enqueue messages.
- `CLPR_INSUFFICIENT_CONNECTOR_BALANCE` (565) - defined for a Connector balance that can't cover the queue fee, including any congestion escalation, but **not currently reachable**: `sendMessage`'s outbound path only checks queue depth (`CLPR_QUEUE_FULL`) and the per-Connector quota (`CLPR_QUEUE_QUOTA_EXCEEDED`) - no balance/fee check exists there today. Don't confuse this with the unrelated, implemented `CONNECTOR_UNDERFUNDED` *reply status* (a different mechanism, checked against the receiving Connector's balance during inbound bundle dispatch, not this response code).

#### Internal

- `CLPR_INTERNAL_STATE_CORRUPTION` (566) - CLPR state is corrupt (e.g. an outbound message ID was assigned but the message doesn't exist in the queue). This should never happen in correct operation; treat it as a bug report, not a caller-input error, and surface it distinctly rather than folding it into ordinary validation-failure handling.

#### Transaction Retry

None of the codes above are transient/node-specific failures in the sense the SDK's existing retry loop targets (e.g. `BUSY`, `PLATFORM_TRANSACTION_NOT_CREATED`).
They are all deterministic validation outcomes based on Channel/Connector/bundle state and should **not** trigger automatic retry with the same transaction body.
`CLPR_RATE_LIMITED` is the one exception worth flagging *once it's actually implemented* (see the note above - it isn't yet): implementers should confirm with the CLPR working group whether it should be added to each SDK's default retryable-status set (analogous to existing throttle-related codes), since a `submitBundle` caller may need to retry the same bundle later once backlog clears.

The mirror node queries return no consensus-node response codes; their HTTP retry behavior is covered under [Mirror node query implementation](#mirror-node-query-implementation) below.

### Mirror node query implementation

- **Transport.** Both queries go through the `Client`-owned `MirrorNodeHttpClient` with a `MirrorNodeRestPath`, as the [HTTP Transport Layer](https://github.com/hiero-ledger/sdk-collaboration-hub/blob/main/proposals/http-transport-layer.md) proposal requires. Neither builds its own HTTP client, retry loop, or identity headers. Errors reach the caller in each query's own error type: `4xx` other than `429` is not retried; `429` / `5xx` follow `MirrorNodeHttpRetryPolicy`.
- **ID encoding.** 32-byte IDs in the equality filters are written as lowercase hex with a `0x` prefix, matching the mirror node design's examples.
- **Validation before the network call.** Every ID must be set and 32 bytes long.
- **Response mapping.**
  - Hex `0x...` strings map to `bytes`.
  - `seconds.nanoseconds` strings map to `dateTime`.
  - `0.0.x` strings map to `ContractId`.
  - `admin_key`'s `{_type, key}` maps to the SDK's `Key`, including `ProtobufEncoded` for key lists and threshold keys.
  - 64-bit integers such as `locked_stake` must be parsed without precision loss; convert stake to `Hbar` through its tinybar representation.
- **Missing entities.** Proposed SDK behavior: an unknown Channel or a Connector with no current non-deleted record fails with a not-found error. For the Connector list, send `deleted=eq:false`; both queries follow pagination before deciding absence. Do not treat retained deleted rows as live Connectors; agree empty-result and ingestion-lag behavior with the mirror node team.

### Integration fixture prerequisites

Keep single-ledger serialization, local validation and mocked-verifier tests separate from real-proof cross-ledger acceptance. CLPR defaults off. The pinned CN single-network/embedded CLPR tasks use mocked signatures; plain dev properties enable CLPR but disable WRAPS. Enabling `clpr.enabled` alone does not establish proof readiness.

Use CN's [multinetwork task](https://github.com/hiero-ledger/hiero-consensus-node/blob/76ba2903da9e9464bdc30149eb931d768ff0fa00/hedera-node/test-clients/build.gradle.kts#L226) and `HieroToHieroBase` as the two-ledger fixture reference. ## SDK Example

This example follows the "Setting up a new route" cross-role scenario: establishing a Channel between two Hiero networks and submitting a first bundle.

1. On Ledger A, select a supported built-in verifier or deploy/reuse a verifier for Ledger B's proof system; obtain its `ContractId`. Do the same on Ledger B for Ledger A's proof system.
2. Generate a keypair for the registrant and choose a 32-byte `channelId`. Obtain `ownershipCommitment` with `ClprRegisterChannelTransaction.computeOwnershipCommitment(channelId, publicKey)`; the helper handles the scheme-specific key encoding. For a Connector, use `ClprRegisterConnectorTransaction.computeConnectorId(channelId, publicKey, salt)` followed by `computeOwnershipCommitment(connectorId, publicKey)`.
3. Submit `ClprRegisterChannelTransaction` with `ownershipCommitment` to Ledger A. Verify the transaction succeeds.
4. Submit the same `ClprRegisterChannelTransaction` (same commitment) to Ledger B. Verify the transaction succeeds.
5. Execute `ClprGetLedgerConfigurationQuery` and `ClprGetEndpointManifestQuery` against Ledger B; wait for non-empty `configurationStateProof` and `manifestStateProof` accepted by the selected verifier and retain the bytes unchanged for Ledger A (and vice versa). Do not infer proof contents from the live configuration fields returned alongside them.
6. Submit `ClprCompleteChannelTransaction` to Ledger A with `channelId`, `setOwnershipProof(privateKey)` using the same registrant keypair from step 2, the verifier `ContractId` from step 1, `configProofBytes` = Ledger B's `configurationStateProof`, and `endpointManifestProofBytes` = Ledger B's `manifestStateProof`. Verify the transaction succeeds.
7. Repeat step 6 symmetrically on Ledger B using Ledger A's proofs.
8. After its proposed REST dependency is implemented, on each ledger execute `MirrorNodeClprChannelQuery` with the `channelId` and verify that its status is `ACTIVE`, waiting for mirror node ingestion without assuming a fixed delay.
9. After registering/funding the route's Connectors and configuring the application callbacks, once an application contract enqueues a message through `sendMessage` and an endpoint relay observes it, verify that a subsequent `ClprSubmitBundleTransaction` submitted by that endpoint against either ledger succeeds.
